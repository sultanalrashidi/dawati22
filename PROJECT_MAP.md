# PROJECT_MAP — دعوتي (Dawati)

Living architecture doc. Code lives in [`web/`](web/) — see [`web/README.md`](web/README.md) for setup/run instructions and demo accounts. This file lives at the repo root next to the design references (`Card Designs/`, `Designs/`, `designd2/` — tracked in the repo as reference material, not part of the running app). `Card Designs/` and `Designs/` are optional inspiration, not copied wholesale. `designd2/` is an exception: 4 of its HTML/CSS mockups (`couture_invitation`, `garden_invitation`, `palace_invitation`, `dawati_master_immersive_experience_v2` + its `shader/` background) were deliberately reviewed and their palettes/fonts/motion ideas ported into 4 new themes, per explicit user request — see "Theme engine" below.

## Stack

- **Framework**: Next.js 16 (App Router, Turbopack, React 19). Note: `middleware.ts` is renamed `proxy.ts` in v16 — see `web/src/proxy.ts`.
- **DB**: PostgreSQL 16 (local via Homebrew for dev: `brew services start postgresql@16`, db `dawati_dev`) + Prisma 7 (`prisma-client` generator, driver adapter `@prisma/adapter-pg`, config in `web/prisma.config.ts`).
- **Styling**: Tailwind CSS v4 (CSS-first config in `globals.css`) + Base UI (`@base-ui/react`) for complex interactive components — plain elements are hand-styled, not a Base UI skin.
- **i18n**: Hand-rolled `app/[locale]/` routing (`ar` default/RTL, `en`/LTR), dictionaries in `web/src/lib/i18n/dictionaries/*.json`. Guest-facing `/i/[token]` pages are always Arabic/RTL, no locale switch (per spec).
- **Theme (light/dark)**: CSS custom properties + `data-theme` attribute, inline no-flash script, cookie-persisted. The light/dark toggle only affects the **app shell** — the guest invitation page's colors are theme-driven (fixed per invitation theme) and don't respond to it, since a "Royal Palace" dark-luxury card shouldn't flip to white on a light-mode phone.
- **Auth**: Custom phone+OTP sessions (no third-party auth lib). DB-backed sessions (`Session` model, hashed token in httpOnly cookie). OTP via pluggable adapter: mock (dev, code shown on-screen) or Authentica (real SMS) — see `web/src/lib/otp/`.
- **Payments**: Pluggable — mock (dev, instant "paid") or Moyasar (Sandbox/production once keys are set), including webhook signature verification and server-side re-verification of the hosted-form redirect — see `web/src/lib/payments/` and `web/src/lib/orders/service.ts`.

## Architecture

Single Next.js app (`web/`), four surfaces:

1. Customer app — `app/[locale]/(events, plans, themes, checkout)/...`, RTL/LTR, light/dark, mobile-first.
2. Guest experience — `app/i/[token]/...`, standalone root layout, no auth, always `ar`/RTL, opened from a WhatsApp link.
3. Admin panel — `app/[locale]/admin/...`, protected server-side by role.
4. Gate staff scanner — `app/[locale]/gate/...`, protected server-side by role, camera QR scan (`BarcodeDetector` API) with a manual-entry fallback. A parallel **no-login** entry point, `app/[locale]/gate-access/...`, serves the same scanner UI to a door guard who never gets a user account — see "Gate-PIN access" below.

**Permissions are enforced server-side**, not by hiding UI: every Server Function calls `requireUserOrThrow(...)` / every protected page calls `requireUserOrRedirect(...)` itself (see `web/src/lib/auth/guards.ts`). `proxy.ts` is intentionally minimal (just the `/` → `/{defaultLocale}` redirect) — Next 16's own guidance warns proxy matchers are easy to silently bypass via refactors, so it's not relied on for auth.

**QR / invitation security**: no sequential IDs. `Invitation.linkToken` and `Invitation.qrToken` are independent 256-bit random tokens (`generateSecureToken()`), unguessable and unrelated to the guest/event ID. Validity is always checked server-side against the DB, never trusted from the client.

**Check-in concurrency**: `performCheckIn()` (`web/src/lib/checkin/service.ts`) deducts a seat via `guest.updateMany({ where: { checkedInCount: { lt: allowedCount } }, data: { increment: 1 } })` inside a transaction — Postgres row-locks the UPDATE, so two simultaneous scans of the last seat can't both succeed. Verified manually against a live scan.

**Theme engine**: themes are rows (`Theme.config: Json`, typed as `ThemeConfig` in `web/src/lib/themes/types.ts`) read by one renderer (`components/guest/invitation-view.tsx`) — adding a theme is a data change, not a new page/component. Editing a theme **already used by a live event** forks a new versioned row and archives the original instead of mutating it in place, so existing guests' invitations never change underneath them (`web/src/lib/admin/themes/service.ts:updateTheme`). Verified manually: editing the in-use "Royal Palace" theme produced `palace-gold` (archived, untouched) + `palace-gold-v2` (published), with the existing event still pointing at the original.

**Theme preview**: `components/themes/theme-preview-dialog.tsx` renders the real `InvitationView` in a Base UI `Dialog`, fed with sample content (no DB record needed) via a `mode="preview"` prop — RSVP is simulated client-side only (never calls `submitRsvpAction`), and the accepted-state QR is a decorative local placeholder (`FakeQr`) rather than a server-generated one. Wired into the admin theme editor (live form state, updates as you edit), the public `/themes` gallery, and the event-creation theme picker — this is how "see and choose" / "see and preview" actually works, not the small static swatch card alone.

**Category decoration kits**: `components/guest/theme-decor.tsx` renders one hand-authored SVG motif per `Theme.category` (luxury/minimal/saudi/romantic/botanical/dark/experimental), colored via that theme's own accent, with a subtle CSS float/sway animation. Every theme in a category automatically gets a distinct decorative personality for free — no per-theme artwork needed. No photo uploads anywhere in the invitation, by explicit product decision (see ORPHANS section).

**Optional background music**: `Event.musicYoutubeId` (nullable) is set by the customer as a plain YouTube link at event creation, parsed via `lib/youtube.ts`. The customer also picks `Event.musicAutoplay` (radio: guest taps to play, or plays automatically the moment the invitation opens) — a labeled pill button (`MusicToggle` in `invitation-view.tsx`, icon + "موسيقى" text so it can't be missed, not just an icon) always shows when a link was set. Autoplay works by appending `&autoplay=1` to the hidden `youtube-nocookie.com` iframe's `src` rather than a post-mount `postMessage` call — it rides the same user gesture that opened the invitation (the cover-tap), which is what lets the browser allow unmuted audio; manual mode leaves the iframe silent until the button's `postMessage("playVideo")`. The theme-preview sample data (`theme-preview-dialog.tsx`) also sets a real, oEmbed-verified royalty-free track so customers see and can try the music button while just browsing themes, not only after creating a real event.

**WebGL shader background**: `components/guest/shader-background.tsx` is a from-scratch raw-WebGL1 canvas component (no `three`/`@react-three` dependency) — a ported, palette-parameterized version of a multi-octave noise "silk flow" fragment shader found in a reference mockup. Opted into per-theme via `ThemeConfig.background = { effect: "shader-silk" }` (currently only `immersive-espresso`). Respects `prefers-reduced-motion` by rendering a single static frame instead of animating.

**"doors" open style**: a 4th theme-opening mechanic (`motion.openStyle: "doors"`, currently only `palace-doors`) — two full-bleed panels rotate open in 3D (`dawati-door-left/right-open` keyframes in `globals.css`) around a central monogram emblem, instead of the plain button or wax-seal badge used by other themes. Cover-state rendering for this branches early in `InvitationView` (`hasDoors`) since the two-panel layout doesn't fit the shared card structure.

**Post-open scene flow (universal, all themes)**: after the cover opens, every theme shows the same sequence of full-height, scroll-snapped scenes instead of one static card. Each scene fades/slides in the first time it's ~30% visible (`useInView` + `IntersectionObserver` in `invitation-view.tsx`, CSS in `globals.css` under `.dawati-scene*`). Current order (final spec, superseding an earlier 4-scene version):
1. **Reveal** — Latin couple names, "دعوة خاصة إلى {guest}", Arabic invitation text, event date in **both Gregorian and Hijri** (`lib/dates.ts`, via `Intl` with the `islamic-umalqura` calendar — no dependency; note Intl's own Hijri formatting already appends the "هـ" era marker, don't append it again).
2. **The two families** — heading + optional short greeting (`Event.familiesGreetingAr`) + groom/bride names and family names side by side (`groomNameAr`/`groomFamilyAr`/`brideNameAr`/`brideFamilyAr`, all optional, falling back to the Latin name if unset).
3. **Countdown** (moved here from scene 1).
4. **"كل ما يهمكم"** — date/time + location + map link + an **add-to-calendar** link (`lib/calendar-link.ts`, a Google Calendar `render` URL — no file generation, no backend).
5. **Event schedule** (`Event.scheduleItems`, `Json` array of `{labelAr, time}`, entered at event creation as `label|time` lines) — scene omitted entirely if empty.
6. **Notes for guests** (`Event.notesAr`, one note per line) — scene omitted entirely if empty.
7. **RSVP form** — name (prefilled from the guest record, editable), phone, attending/not toggle, party size (dropdown capped at `Guest.allowedCount` — never free entry, protects the seat-capacity model), and a free-text message, all persisted on the `Rsvp` row (`guestNameAr`/`guestPhone`/`partySize`/`messageAr`). Replaces the earlier plain accept/decline buttons.
8. **Outcome** — QR pass (ACCEPTED) or apology message (DECLINED), as before.

Ported from a reference mockup's own scene structure and content list, applied to all 47 themes without exception per explicit request — only the cover screen (each theme's own open-style: plain scan-line indicator, wax seal, or doors), palette, fonts, decoration kit, and (for `split-portrait` layouts) a persistent side accent bar still differ per theme. The 4 card "layouts" now only shape the **cover** screen, not the post-open content.

**Decoration kit redesigns**: `LuxuryKit`'s original curved corner flourish and `ExperimentalKit`'s floating dots were both explicitly disliked by the user ("looks old" / "must change"). Replaced with: `LuxuryKit` → 4 small quarter-round corner brackets (same visual language as the personalization-scene frame it's echoing); `ExperimentalKit` → two faint vertical guide lines plus a single accent line that continuously scans top-to-bottom (`dawati-decor-scan` in `globals.css`), a more contemporary/techy motif.

**Gate-PIN access (login-free door scanning)**: an alternative to assigning a `GateStaff` user account per event. Every `Event` gets a `referenceCode` (6-char human-typeable code, unambiguous alphabet excluding 0/O/1/I/L, generated once at creation via `lib/events/reference-code.ts`, retried on the rare unique-constraint collision — `lib/events/service.ts:createEventWithUniqueReferenceCode`). The owner can additionally set a 4-8 digit PIN (`Event.gatePinHash`, sha256 at rest, same convention as OTP codes) from `/events/[eventId]` (`components/events/gate-pin-form.tsx`). A guard visits the public `/[locale]/gate-access` route (reachable from an always-visible header icon, no login), enters the reference code + PIN, and on success gets a signed grant: `lib/gatepin/session.ts` mirrors `lib/auth/session.ts`'s pattern exactly but with its own DB-backed table (`GateAccessSession` — hashed opaque token in an httpOnly cookie, 12h TTL) instead of reusing the user-`Session` model, since this grant is scoped to one event, not one user, and needs independent revocation (clearing the PIN also deletes any live `GateAccessSession` rows for that event). Wrong-PIN attempts are rate-limited per event (`Event.gatePinFailedAttempts`/`gatePinLockedUntil`, 5 attempts → 15 min lockout), modeled directly on `lib/otp/service.ts`'s window/lockout pattern. `GateScanner` (`components/gate/gate-scanner.tsx`) was refactored to accept a `scanAction` prop instead of importing `scanQrAction` directly, so the exact same scanner component serves both the authenticated `/gate/[eventId]` path (`scanQrAction`, real `GateStaff`/`ADMIN` session) and the no-login `/gate-access` path (`scanQrPinAction`, verifies the gate-session cookie instead of a user session) — both ultimately call the same `performCheckIn(qrToken, eventId, gateStaffId)`, with PIN-based scans passing `gateStaffId: null`, the same code path already used for ADMIN scans (no `CheckInLog` entry gets written for null-staff scans, an accepted pre-existing trade-off, not new to this feature). Verified live end-to-end: reference code + PIN issued, wrong PIN rejected, 5 wrong attempts triggered the lockout message (and blocked even the correct PIN until it expired), correct PIN granted a scanner session, a real QR token was checked in and the seat count/invitation status updated correctly in Postgres, and "exit" tore down the session row.

**Client/server boundary gotcha worth remembering**: never import `@/generated/prisma/client` (even just for an enum) into a `"use client"` file — it pulls the whole Prisma runtime into the browser bundle and produced a genuine Turbopack build panic (`chunking context does not support external modules (request: node:module)`) during this build. Client components that need an enum-shaped value use a local plain string-union type instead (see `components/gate/gate-scanner.tsx`'s `GuestFacingStatus`-style pattern, and the fix applied to `theme-status-actions.tsx`).

## Data model (Prisma — `web/prisma/schema.prisma`)

`User` (role: CUSTOMER/ADMIN/GATE_STAFF), `Session`, `OtpCode` · `Plan`, `Order` · `Theme`, `ThemeAsset`, `ClientAssignedTheme` · `Event` (incl. `referenceCode`, `gatePinHash`, `gatePinFailedAttempts`, `gatePinLockedUntil`) · `Guest`, `Invitation`, `Rsvp` · `GateStaff`, `GateStaffAssignment`, `CheckInLog`, `GateAccessSession` (login-free guard grants — see "Gate-PIN access" above) · `GuestManagementRequest`, `Notification`, `AuditLog`.

`Invitation.status` holds the delivery/RSVP lifecycle the app actually writes (DRAFT/SENT/VIEWED/ACCEPTED/DECLINED/BLOCKED/CANCELLED); the entry-validity refinements (VALID/PARTIALLY_USED/FULLY_USED/EXPIRED) are valid enum members reserved for admin override / gate-scan display rather than written automatically, since they're derived from seat counts + expiry at read time.

| Buy a plan / create an order | ✅ (own) | ❌ | — (admin plan/price management instead) |
| Create/edit own event | ✅ (after a PAID order) | ❌ | ✅ (any, via admin panel) |

**Bugs found and fixed during manual verification** (kept here since they're the kind of thing worth re-checking after similar changes):
- The desktop nav (`Plans`/`Themes`/role link — `My Events`, `Admin`, or `Gate`) in `site-header.tsx` was `hidden sm:flex` with **no mobile fallback at all** for the role-based links — only a hardcoded `/themes` icon existed for phones. A signed-in customer or admin navigating to the homepage on mobile had no way back to their own dashboard (user report: "the whole path is one-way, no way back, even on the admin account"). Fixed by making that mobile-only icon role-aware (`quickNav` in `site-header.tsx`): signed-out → Themes, `CUSTOMER` → My Events, `ADMIN` → Admin dashboard, `GATE_STAFF` → Gate scanner. Also removed the light/dark toggle button from the header per user request (declutter; the underlying theme system is untouched, just no visible switch anymore — `theme-toggle.tsx` deleted as dead code).
- Login form mapped every non-`invalid_code` OTP error to "invalid phone", so a blocked account showed a misleading message instead of "account blocked" — fixed by matching all three `OtpSubmitResult` error variants explicitly (`components/auth/login-form.tsx`).
- `ThemePreviewDialog`'s trigger wrapped a `<button>` inside `Dialog.Trigger`'s own `<button>` — invalid HTML that Base UI/React flagged as a hydration error and which silently broke click handling. Fixed with Base UI's `render` prop (`Dialog.Trigger render={<button>...} />`) instead of children — this is the correct pattern any time a Base UI trigger/close needs to render as a caller-supplied element.
- The `/themes` gallery mounted one independent `Dialog.Root` **per theme card** (43 of them at once) — clicking one theme's preview button would sometimes open a different theme's content, or nothing, reproducible in both dev and production builds. Root cause: too many simultaneously-mounted Base UI dialog instances, not an HMR/dev artifact. Fixed by refactoring to the single-shared-dialog pattern already used correctly in `ThemePicker`: `ThemeGalleryCard` (`components/themes/theme-gallery-card.tsx`) is now presentational-only (`onPreview` callback, no `Dialog` inside it), and a new `ThemeGalleryGrid` (`components/themes/theme-gallery-grid.tsx`) holds one `previewId` state + one `ThemePreviewDialog` instance for the whole grid. **Rule of thumb**: never mount one modal instance per list item — hold one shared dialog instance keyed by a selected-id state instead.
- Once the dialog above became shared/reused across theme switches, `InvitationView`'s internal cover/RSVP state leaked across previews — previewing theme A through to "accepted", then switching to theme B, showed B already in the accepted/pass state. Fixed by adding a `previewKey` prop to `ThemePreviewDialog` (passed as the theme's `id` from both call sites) applied as `key={previewKey}` on `InvitationView`, forcing a clean remount on every theme switch. Verified: opening theme A → accept RSVP → close → open theme B now correctly starts at the cover screen.
- The `immersive-espresso` shader's first WebGL implementation looked completely blank (transparent canvas) despite compiling and drawing without any `gl.getError()`. Root cause was actually **two** stacked bugs: (1) a strict-ESSL-1.00 issue — `vec3(0,0,0)`-style bare integer literals inside constructors aren't implicitly float-converted on all drivers, so several `noise()` helper calls silently failed to compile until every literal became `0.0`/`1.0`; (2) even after that fix, sampling the canvas from a **separate** JS call via `gl.readPixels`/`drawImage` always read back zeros — this is expected WebGL behavior (`preserveDrawingBuffer: false` means the browser is free to clear the drawing buffer right after compositing each frame), not a rendering bug. The actual proof came from `console.log`-ing `gl.readPixels` **synchronously inside the same `requestAnimationFrame` callback**, right after `gl.drawArrays` — that showed correct, non-zero, palette-derived pixel values every frame. **Rule of thumb**: never trust an out-of-band pixel readback for a `preserveDrawingBuffer: false` canvas; verify from inside the draw call itself (or set `preserveDrawingBuffer: true` temporarily while debugging).
